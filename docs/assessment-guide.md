# CDDA 游戏评估与改进指南

> 本文档记录游戏子系统评估的方法论和改进模式，供后续迭代参考。

---

## 一、评估方法论

### 1.1 评估维度

每个子系统从以下四个维度审查：

| 维度 | 关注点 | 检查方法 |
|------|--------|---------|
| **功能完整性** | 系统是否实现了设计目标的全部功能 | 对照设计文档/Constants 配置，逐项检查有无缺失 |
| **系统联动** | 子系统之间是否正确连接 | 追踪数据流：A 的输出是否被 B 消费，B 的输出是否触发 C |
| **用户体验** | 界面/交互是否友好、有无歧义 | 模拟玩家操作流程，注意提示、反馈、边界情况 |
| **代码质量** | 是否有未使用的字段/方法、硬编码、竞态风险 | 静态分析 + 人工审查 |

### 1.2 审查步骤

```
1. 列出子系统的所有文件（grep / find）
2. 阅读核心逻辑文件，标记关键路径
3. 追踪输入 → 处理 → 输出的完整链路
4. 检查依赖方是否正确消费了输出
5. 查找未使用的字段、方法、配置
6. 检查边界条件（空值、零值、溢出、并发）
7. 模拟用户操作流程，记录体验问题
```

### 1.3 问题分级标准

| 级别 | 标记 | 定义 | 修复时限 |
|------|------|------|---------|
| 🔴 严重 | Critical | 核心功能缺失或阻断，玩家无法正常使用某系统 | 立即修复 |
| 🟡 高 | High | 功能可用但体验差，或存在发布风险 | 下一轮修复 |
| 🟢 中 | Medium | 体验瑕疵或代码异味，不影响核心流程 | 有空时修复 |
| ⚪ 低 | Low | 锦上添花，纯优化性质 | 排期后修复 |

### 1.4 分类标识

| 分类 | 含义 |
|------|------|
| **已修复 ✅** | 代码已修改，测试通过 |
| **设计意图（不修复）** | 经确认是设计决定，非 Bug |
| **待修复** | 已确认问题，待排期 |
| **已确认存在** | 代码已实现，评估时为误判 |

## 二、改进模式

### 2.1 模式 A：补全缺失链路（最常见）

**适用场景**：系统 A 输出了数据，但系统 B 没有消费。

**改进步骤**：
```
1. 确认 A 的产出（方法返回值 / 状态字段）
2. 确认 B 应该消费的位置（update 方法 / 事件回调）
3. 在 B 中新增消费逻辑，避免修改 A（保持低耦合）
4. 新增状态判定方法（如 calcXXXDamage()），返回伤害值而非直接扣血
5. 在调用方（GameScene / Screen）统一结算，保持管理器职责单一
6. 添加日志反馈，让玩家知道发生了什么
```

**案例**：代谢死亡判定
- MetabolismManager 计算了体温/能量，但没有伤害逻辑
- HydrationManager 计算了水分，但没有伤害逻辑
- 改进：在两个管理器中新增 `calcXXXDamage()` 方法，GameScene 统一调用并扣 HP
- 不修改管理器的 update 流程，只新增查询方法

### 2.2 模式 B：验证已有实现

**适用场景**：评估报告标记为"缺失"，但代码已存在。

**验证步骤**：
```
1. 按文件列表逐一确认实现状态
2. 检查注册/绑定是否生效（如 ItemActionRegistry.register）
3. 检查数据配置是否完整（如 vegetation drops 字段）
4. 检查调用链路是否畅通（从 UI → Action → System → 结果）
5. 更新评估报告，修正误判
```

**案例**：植被交互接口
- 评估报告说"无 Harvest/Plant 实现"
- 实际已有 ChopTreeAction / GatherPlantAction / PlantSeedAction / HarvestCropAction
- 全部 20 种植被定义均有 drops 配置
- 改进：更新评估报告，将误判改为"已确认存在"

### 2.3 模式 C：新增枚举 + 联动

**适用场景**：需要扩展死亡原因/状态类型等枚举值。

**改进步骤**：
```
1. 在枚举中新增类型（如 DEHYDRATION、TEMPERATURE）
2. 更新相关判定方法（如 isNatural() 包含新类型）
3. 在调用方新增判定逻辑（检查条件 → 触发新类型）
4. 添加对应的反馈信息（日志/消息）
5. 预留后续扩展点（如游戏结束画面 TODO）
```

### 2.4 模式 D：UI 体验优化

**适用场景**：界面交互不友好、语义不清、操作效率低。

**改进步骤**：
```
1. 定位问题 UI 组件和对应代码行
2. 分析现有交互模式（参考同模块其他组件）
3. 添加快捷操作（PgUp/PgDn 批量调整）
4. 增加视觉区分（颜色编码区分状态）
5. 修正语义歧义（Enter 行为统一）
6. 更新帮助文档（新操作需要说明）
```

## 三、文档结构模板

每次评估报告应包含以下结构：

```markdown
# [子系统名称] 评估报告

> 评估时间、范围、方法

## 修复记录

### 已修复 ✅
| # | 问题 | 修复内容 | 文件 |

### 设计意图（不修复）
| # | 问题 | 设计理由 |

### 待修复
| # | 优先级 | 问题 | 建议 |

## 按模块评估

### 🟢 良好（无问题或已修复）
### 🟡 需要改进（高/中优先级问题）
### 🟢 小问题（低优先级）

## 修复优先级建议

### 第一轮（核心功能）
### 第二轮（体验提升）
### 第三轮（完善细节）
```

## 四、关键检查清单

### 4.1 代谢/生存系统必查项

- [ ] 能量/水分/体温是否有危险阈值警告
- [ ] 危险状态是否联动 HP（生存系统核心张力）
- [ ] HP 归零是否触发死亡处理
- [ ] 死亡原因是否正确分类（区分饿死/渴死/失温）
- [ ] 是否有对应的恢复手段（食物/水/保暖）

### 4.2 植被/物品系统必查项

- [ ] 每种植被是否有 drops 定义
- [ ] 每种交互动作是否注册到 ItemActionRegistry
- [ ] 动作是否有 canExecute 检查（避免空操作）
- [ ] 动作是否有方向选择需求（needsDirection）
- [ ] 种子 → 作物映射是否完整（producesCrop 字段）
- [ ] 收获是否检查成熟度（GrowthStage.MATURE）

### 4.3 UI/交互必查项

- [ ] 列表是否有滚动支持（超出时是否截断）
- [ ] 确认键是否语义清晰（Enter vs ← 的区别）
- [ ] 是否有批量操作快捷键
- [ ] 状态区分是否有视觉标记（颜色/图标）
- [ ] 帮助文档是否覆盖新功能
- [ ] 边界情况是否有提示（背包满、无可操作目标等）

### 4.4 代码质量必查项

- [ ] 是否有未使用的字段/方法（IDE 警告）
- [ ] 是否有硬编码常量（应提取到 Constants）
- [ ] 是否有空指针风险（null 检查）
- [ ] 是否有并发问题（后台线程写入共享状态）
- [ ] 日志是否有级别区分（debug/info/warn/error）
